## 2. 源码确认的实质问题

### 可导入不代表模型可用

`p1/search.py::_optional_embedder` 只尝试导入依赖，模型在 `_load_embed_model` 中延迟构造。`retrieval.py::_embedder_available` 只检查返回函数是否非空，不能证明模型已在本地、加载成功或查询嵌入成功。

### 向量失败后 BM25 被当成向量路加入融合

`JsonlCorpus.vector_search` 捕获异常后返回 `bm25_search`。`_search_generic_hybrid` 随后仍把非空结果加入融合列表。因此依赖可导入、实际向量失败时，可能得到 keyword + BM25 + BM25，而非干净的两路回退。

评测需记录 requested_strategy、effective_channels、fallback_reason、每路耗时及实际模型指纹；缺少必需通道的基准应 fail closed 或明确作为降级组另报，不能仍统称相同 hybrid。

### 查询包含自动重建和写盘

`vector_search → index_records → persist` 在内容签名不同时重嵌入并保存。八个 JSONL 未变不代表评测链路只读；读取侧剥离、去重及规范化变化也会改变实际索引输入。

审核时读取但未重建的现状：

| 手册 | 原始 sections 行 | 当前读取后行 | 磁盘向量条数 | 内容签名一致 | 索引修改时间 |
|---|---:|---:|---:|---|---|
| anquan | 1474 | 1355 | 1344 | 否 | 05:08:32 |
| duli | 1788 | 1494 | 1489 | 是 | 12:55:29 |

以上为审核时现状，不能反推 1112 当时全部状态。anquan 下一次正式向量查询存在重建风险。

### duli 的 1489 不是“应该有 1473 行”的直接证据

当前实际读取后有 1494 行，但 `_doc_id` 唯一值为 1489。重复 ID 多出的五行来自四组，其中登录管理面 ID 有三行，其余三组各两行。持久化按 ID upsert，会产生覆盖风险。不能拿旧轮读取计数与当前索引数量直接断言索引损坏。

应先解决非等价内容同 ID 的身份契约，并验证每个向量的 doc_idx 与当前语料一致。仅存文本 content_sig 不足以证明 ID、映射和模型都匹配。

### 持久化模型签名没有真正保存

`VectorIndex._note_indexed_sig` 只把 content 保存到 store；`_restore_sig_from_store` 使用当前 embedder 签名拼接旧 content。磁盘 metadata 无模型指纹字段。换模型且文本不变时，可能错误接受旧模型向量。这是源码确认的契约漏洞，不是本次 16 处差异的已证实原因。

## 5. 建议下一最小任务

先暂停词表调优，完成“评测有效通道可观测 + 隔离索引写入”小闭环：

1. 保存当前两手册数据、索引与代码指纹，不覆盖历史证据。
2. 在独立运行目录复制固定输入及索引，所有对照仅使用副本。
3. 为向量成功、依赖缺失、模型加载失败三种路径记录真实通道，禁止将失败回退伪装成向量路。
4. 用 stub 验证通道契约，再在有超时且明确离线本地模型配置的真实链上验证一个开发集反例；不能以 stub 代替真实效果。
5. 保存 stdout/stderr、命令、模型指纹、预处理后语料/ID 映射哈希、索引前后哈希。以两次独立进程的一致结果确认可复现后再做词表消融。

持久化模型签名和同 ID 异内容问题另列高优先级最小任务，不在同一轮顺手大改。人工审核、录制接入、Wiki 新功能不应掩盖当前基准有效性缺陷。
