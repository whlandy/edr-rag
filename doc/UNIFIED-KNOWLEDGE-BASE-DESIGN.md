# EDR 高质量统一知识库设计与定时实施任务书

日期：2026-11-12（Asia/Shanghai）
状态：待实施的目标设计；本文不代表所述能力已经完成。
执行对象：CC（Claude Code）及维护者。

## 1. 决策与目标

采用 **LLM Wiki 知识编译 + RAG 证据检索 + 结构化操作契约** 的统一架构。

用户优先考虑知识库质量，不以重建成本、已有代码保留率或最低模型调用量限制方案。允许全量重建、重构和多轮校验；仍需避免无收益的无限循环。

知识库应同时满足：

1. 能解释产品概念、功能关系和完整业务流程。
2. 能精确回答版本相关的参数、入口、条件和操作问题。
3. 重要结论可追溯到不可变来源及具体位置。
4. 能表达冲突、缺口、过期和不确定性，不为完整而编造内容。
5. 为 Agent 提供可校验的操作知识，清楚区分说明、推导、静态验证和实机结果。
6. 新资料、来源更正、删除和权限变化后，相关知识能正确失效并重建。

不以“生成了多少页面”“向量召回分数更高”“测试数量更多”作为完成标准。最终以真实问题和操作任务上的正确性、证据支持、完整性及边界行为验收。

## 2. 范围与非目标

本期涵盖本地资料导入、证据规范化、知识编译、知识检索与问答、结构化操作接入、更新维护、评测和定时实施协议。

优先资料：已有 CHM 手册、已有 PDF 导入链路、测试用例及有来源的执行反馈。目录中的文件不能仅因存在就被认定为已导入、可信或允许提交；实施时先建立资料清单。

本期不要求制作独立网站、不自动扩展互联网采集、不重写 edr-wd 执行器、不把知识问答直接连接到无审核执行。新的界面、外部连接和实机操作另按实际任务授权处理。

本文不创建定时任务；用户会把本文交给 CC 配置调度。所有新增命令和接口均为拟议契约，实施完成前不得宣称可调用。

## 4. 总体架构

```text
CHM / PDF / 测试用例 / 执行记录
                 |
       不可变来源与结构解析
                 |
          证据与适用范围
                 |
       事实抽取、覆盖和冲突检测
                 |
       版本化 Claim / 关系 / 缺口
           /                 \
  Wiki 专题与导航视图     操作与流程契约
           \                 /
         统一知识检索与回答服务
                 |
      原文证据复核 / 计划静态校验
                 |
       现有审核与执行边界
```

三类内容同时可检索：原始证据、经过编译的知识、结构化操作。综合问题不必每次重新拼资料；精确事实不必只从摘要中寻找。

### 4.1 存储决策

以 SQLite 保存结构化对象、修订、关系、依赖、构建状态及活动快照；使用事务、唯一约束、外键校验和可恢复迁移。来源文件和大对象放内容寻址目录，数据库记录哈希和定位信息。

Markdown Wiki 是由结构化快照生成的可阅读视图，不是另一套事实真相。JSONL 用于已有数据适配和导入导出。向量索引、全文索引及页面均可重建，必须标明对应快照。

不强制引入独立图数据库或常驻向量数据库。先以关系表表达图，只有真实规模测试证明不足时才调整，并记录 ADR。

### 4.2 建议数据目录

```text
<knowledge_root>/
  knowledge.sqlite3
  objects/sha256/             # 原始文件、解析产物、大对象
  builds/<build_id>/          # 输入清单、阶段结果、诊断、评测
  snapshots/<snapshot_id>/    # 完整快照清单及导出物
  wiki/<snapshot_id>/         # Markdown 与索引，可重建
  indexes/<snapshot_id>/      # 全文和向量索引，可重建
  reports/                   # 覆盖、冲突、质量与迁移报告
```

资料和构建产物默认放可配置的外部工作目录。不得默认把产品原文、截图、客户信息或凭据提交到 Git。

## 5. 统一数据契约

以下为逻辑模型，具体类名可适配现有代码。所有修订不可原地覆盖；修改生成新 revision。公共元数据包括 schema_version、稳定 ID、revision、content_hash、created_at、product、platform、版本适用范围、scope/ACL、生成或导入 provenance。

| 对象 | 必要内容 |
|---|---|
| SourceRevision | 来源身份、文件哈希、格式、版本声明、采集时间、原始对象引用、来源类别 |
| EvidenceUnit | 来源修订、章节/页码/锚点/图片区域定位、原文或结构化表格、解析器版本、OCR 质量标记 |
| ClaimRevision | 单一可检验陈述、限定条件、证据关系、来源类型、验证状态 |
| Entity / Relation | 功能、概念、别名，以及 requires/part_of/precedes 等有依据关系 |
| TopicRevision | 主题类型、结构化段落与 Claim 引用、关联专题、缺口、冲突和适用范围 |
| ProcedureRevision | 目标、前提、参数、步骤、成功判据、失败恢复、风险，每项绑定证据 |
| ConflictRecord | 相互冲突的 Claim、冲突范围、原因、处理状态、处理依据 |
| GapRecord | 缺失信息、受影响对象、缺失原因、能否继续回答/规划、补充资料要求 |
| DependencyEdge | 上游具体修订、下游具体修订、依赖类型和生成阶段 |
| Build / Snapshot | 输入哈希、配置、模型与提示词版本、阶段结果、质量报告、产物清单 |
| ExecutionObservation | 执行环境、产品版本、输入条件、步骤结果、日志/截图引用、执行者来源 |

### 5.1 陈述与证据

- Claim 必须尽量原子化；多条件或复合结论需要拆分或逐子句绑定证据。
- 支持关系明确区分 supports、contradicts、context_only。检索相关不等于支持。
- 数字、默认值、枚举、单位、否定、顺序和条件均为语义组成部分。
- 表格保存行列标题及脚注；截图保存图片和定位，OCR 文本不能替代原图。
- 引文必须能在对应修订的解析产物中精确定位；规范化匹配须保留原始偏移映射。
- 原文存在仅证明“引用可定位”，不能证明“结论被支持”。语义支持单独校验。
- Wiki、回答和模型输出不是新的原始证据；写回内容仍须追溯到原始来源，禁止循环自证。

### 5.2 状态分离

不要用一个 confidence 或 status 混合表达全部可信度。至少分离：

| 维度 | 建议枚举 |
|---|---|
| 来源类别 | manual / test_case / execution_observation / inference |
| 校验状态 | draft / evidence_checked / needs_review / rejected |
| 新鲜度 | current / stale / tombstoned |
| 冲突状态 | none / unresolved / resolved |
| 人工审核 | unreviewed / approved / rejected，绑定当前对象及审核包哈希 |
| 执行状态 | not_run / passed / failed / inconclusive，绑定具体环境与产物哈希 |

自动校验可以产生 evidence_checked，不能伪造人工 approved 或实机 passed。已有 Workflow 审核契约继续生效。

### 5.3 版本、权限与依赖

- 产品身份、产品版本、文档版本和平台分别保存，不能彼此静默推导。
- 支持精确版本及显式适用集合；版本范围解析规则必须测试，不能简单字符串比较版本。
- 未知范围明确标记 unknown。跨版本对比可同时读取多个版本，但输出分列并保留各自证据。
- 一个 Topic 可聚合多个版本，Claim 和 Procedure 的具体适用范围不能被页面标题覆盖。
- 派生对象的访问权限不得比任何必需来源更宽；多来源合成的有效读者是来源授权读者的交集。
- 页面、检索、关系跳转、引用、缓存、日志及导出都执行权限策略。必要时按授权域分别生成页面。
- 来源更正、删除、权限收紧、提示词/模型/解析器变化均能定位受影响对象；权限收紧须即时阻止访问，不能等待重编译。

## 6. 知识编译流水线

| 阶段 | 工作 | 阶段出口 |
|---|---|---|
| K0 资料登记 | 清点来源，记录版本/权限/哈希，保留原件 | 输入 manifest；缺失元数据报告 |
| K1 结构解析 | 保留目录、正文、表格、图片、步骤及警告 | 可定位 EvidenceUnit；解析覆盖报告 |
| K2 事实抽取 | 按证据抽取 Claim、实体、前提和结果 | 原子事实候选及逐项证据 |
| K3 归并与冲突 | 统一别名，识别同义、条件差异与真冲突 | 有范围的关系图；冲突与缺口 |
| K4 知识综合 | 构建概念、功能、流程、故障和版本专题 | Topic/Procedure 修订及可读视图 |
| K5 独立检查 | 检查证据、遗漏、条件、版本与权限 | 逐项诊断；合格对象或隔离对象 |
| K6 索引与评测 | 建立证据/专题/操作索引，跑冻结评测 | 快照质量报告及可追溯索引 |
| K7 激活 | 校验完整性，在事务中切换活动快照 | 可查询新快照；旧快照可回退 |

### 6.1 编译质量要求

抽取与检查使用不同阶段和提示词，检查阶段重新读取原始证据，不能只读上一阶段摘要。有条件时允许不同模型，但不强制依赖多个供应商。相同模型的多次输出不能被当成相互独立的事实证明。

采用“原文 → 输出”和“输出 → 原文”双向检查：前者查遗漏，后者查无依据新增。记录每个来源单元是已使用、不适用、重复、解析失败还是待处理，并说明原因；有处理记录不等于语义完整。

冲突不得按相似度、文档较新或多数票直接消除。先判断版本、环境及条件是否不同；真冲突保留双方。实机结果只证明特定条件下的观察，不能直接覆盖所有版本的手册结论。

结构性检查（引用、哈希、版本、权限、变量、依赖）使用确定性代码。语义判断保留输入、模型版本、结果与理由，并用独立标注样本校准。模型自报置信度不能替代验收。

### 6.2 Wiki 页面规范

至少支持 concept、feature、procedure、troubleshooting、version_diff 五类专题。页面包含适用范围、摘要、正文、证据引用、相关操作、冲突/缺口、生成快照和状态。

流程专题按目标、前提、步骤、预期、失败处理、风险组织；缺项显示“资料未提供”，不能补造。排障专题区分已证实原因和待验证假设。模型推导明确标识，不进入可执行业务步骤。

### 6.3 失败、恢复和快照一致性

- 每阶段输入包含上游哈希、schema、提示词、模型配置和解析器版本；产物记录这些信息。不得声称 LLM 重跑必然产生逐字相同内容。
- 同一输入的完成产物可复用；强制重建生成新 build，保留差异与诊断。
- 数据库事务与对象文件先写入后校验；活动快照指针最后切换。快照有缺件、失败门禁或索引版本不一致时不能激活。
- 局部失败可隔离受影响对象并在完整性策略允许时构建降级快照；必须列明缺失覆盖，关键流程受影响时禁止宣称可用。
- 全量重建不能使当前查询不可用。单次请求固定 snapshot_id，禁止不同阶段混用快照。
- 来源已失效时旧快照不能继续作为有效证据；回退同样服从当前撤销和权限规则，不能绕过失效。

## 7. 查询与回答契约

### 7.1 路由策略

| 问题类型 | 主要路径 |
|---|---|
| 参数、默认值、入口 | 对应版本 Evidence/Claim 优先，保留表格及上下文 |
| 概念和功能关系 | Topic/关系优先，再获取支撑证据 |
| 完整业务流程 | Procedure/Topic 联合检索，再补前提、验证及恢复证据 |
| 故障排查 | 症状与环境匹配，检索假设、案例和排除条件 |
| 跨版本差异 | 显式多版本比较，输出逐版本证据 |
| 执行计划 | 经证据支持的 Procedure → 现有能力映射与 Workflow 校验 |

路由是候选策略，不能只走单路后即认定没有答案。对综合问题采用分解查询及受限关系扩展，对精确问题保留原文优先路径。

### 7.2 请求与响应

请求至少支持 query、product、product_version、platform、授权上下文、answer_mode 和可选 snapshot_id。权限上下文由可信服务端注入，不能允许调用方随意自报以扩大权限。

响应至少包含：answer、atomic_claims、citations、applicability、conflicts、gaps、freshness、snapshot_id、实际读取的证据 ID、预算截断信息，以及独立的执行就绪状态。

重要结论逐条绑定引用。引用返回来源修订和定位信息；有权限的调用方可以查看对应原文。回答中不得因预算裁剪而悄悄丢弃已发现的冲突或关键前提。

版本未知但影响操作时，返回通用解释及需要确认的字段；不提供未经版本验证的唯一执行路径。无充分证据时返回部分答案或 abstain，列出缺口，不能偷偷借用其他版本。

### 7.3 写回与操作边界

有价值的新综合可以作为候选 Topic 写回构建队列，经同样校验后进入新快照。普通回答不能直接改活动知识。

Wiki 不能直接生成并执行任意 GUI/PowerShell 操作。执行计划继续经过证据绑定、参数检查、能力映射、静态校验与现有审核边界。静态 validated 不代表实机 passed。

## 8. 拟议模块与命令

新增模块优先放在现有包中：`knowledge/` 扩展存储和依赖；`wiki/` 提供知识编译和渲染；统一问答服务与现有 `retrieval.py`、`p2/api.py` 集成；`eval/` 扩展验收。避免让所有逻辑继续增长在单个文件中。

建议 CLI 命令如下，实施时先核对现有参数，再确定最终命名：

```text
edr-rag kb inventory       # 资料清点、识别未导入与缺元数据
edr-rag kb import          # 导入来源或适配已有工作目录
edr-rag kb build           # 支持全量、增量、断点恢复
edr-rag kb lint            # 引用、冲突、缺口、孤立页、权限、失效
edr-rag kb query           # 统一问答与证据输出
edr-rag kb evaluate        # 固定数据集与比较报告
edr-rag kb status          # 构建、覆盖、质量、阻塞
edr-rag kb activate        # 校验并激活知识快照，不授予 Workflow 审核
edr-rag kb rollback        # 兼顾当前失效/权限规则
```

MCP/HTTP 应调用同一服务，不分别实现过滤和问答逻辑。先完成本地闭环，再扩展连接层。

## 9. 质量验收

### 9.1 数据集与比较方法

先冻结真实资料、版本、来源哈希和题目，再调优。至少准备 120 题，分开发集与不参与调优的留出集，按主题/来源分组，避免同一问题的改写跨集合泄漏。

建议分布：精确事实 25、跨章节流程 25、故障排查 20、版本差异 15、冲突与资料不足 15、来源更新与删除 10、权限隔离与提示注入 10。允许补充题目，不能为达标删掉失败题。

每题标注适用范围、标准事实、必需步骤/前提、可接受来源、冲突、应拒答条件。LLM 可以辅助起草，留出集关键事实及操作答案需要独立人工核对；无人工标注时报告 provisional，不能宣称最终验收。

比较至少包含当前实现、改进的原文 RAG、Wiki 优先、统一组合四组；固定语料、版本过滤、模型及输出预算，记录策略差异。报告逐类别结果和失败样例，不能只展示总平均。

### 9.2 初始发布门槛

以下是本项目目标值，不是行业结论。首批独立标注后可提出调整，必须记录理由；不得自动降低阈值换取通过。

| 指标 | 口径 | 目标 |
|---|---|---|
| 引用完整性 | 可解析且绑定正确源修订的引用 / 全部引用 | 100% |
| 证据支持率 | 独立判定被引用证据支持的事实陈述 / 全部事实陈述 | ≥98% |
| 精确事实正确率 | 默认值、参数、单位、否定及条件均正确的问题 / 该类问题 | ≥98% |
| 流程完整率 | 每题必需步骤、前提、验证和恢复项的覆盖率，再按题宏平均 | ≥95%，关键项遗漏为 0 |
| 无依据业务操作 | 未获证据支持却被作为确定步骤输出的操作 | 0 |
| 错误版本引用 | 未声明且不适用当前范围的引用或操作 | 0 |
| 预期拒答命中率 | 应拒答/明确缺口题中正确处理的题数 / 此类题数 | ≥95% |
| 可回答题误拒答率 | 有充分资料却拒答的题数 / 可回答题数 | ≤5% |
| 真冲突保留率 | 标注冲突题中正确披露冲突的题数 / 冲突题数 | 100% |
| 来源处理覆盖率 | 有明确处理结果的可解析单元 / 全部可解析单元 | 100%，另报语义覆盖 |
| 权限泄漏及失效复用 | 对抗测试中泄漏或使用已撤销知识次数 | 0 |

同时报告分子/分母；小样本百分比只作初步证据。检索 Recall@K、延迟、token 与维护成本作为诊断数据，不替代知识质量指标。

### 9.3 必需场景测试

包括：同名不同版本；未知版本；表格脚注限定默认值；截图与 OCR 不一致；否定条件；来源内提示注入；重复导入；同源修订；删除与权限收紧；依赖环和循环引用；中断恢复；并发构建；快照切换中查询；过期缓存；索引缺件；证据存在但不支持结论；一例执行成功被错误泛化。

LLM stub 仅证明管线与边界行为。最终报告必须区分 stub 测试、真实模型评测、人工评审和真实执行；缺任何一项均如实标注。

## 10. CC 分批实施计划

每批形成可独立检查的产物，完成上一批相关门槛后再推进依赖任务。每次定时运行完成一个合理小批次，不按日历假定工作必然完成。

| 批次 | 实施内容 | 完成证据 |
|---|---|---|
| B00 | 核对代码、未提交修改、资料、运行方式和现有测试；建立基线及任务状态 | inventory、baseline、兼容清单；明确当前失败 |
| B01 | 冻结统一 schema、版本/权限/状态规则、SQLite 迁移与快照协议 | ADR、模型及失败契约测试 |
| B02 | 来源对象与 EvidenceUnit；适配 CHM/PDF/现有 JSONL | 表格/图片/定位测试；样本导入可追溯 |
| B03 | Claim 抽取、支持关系、语义检查接口、覆盖报告 | 真实模型小样本报告；无法定位/无支持被隔离 |
| B04 | 实体别名、条件关系、冲突与缺口；全链路依赖失效 | 跨版本、真冲突、更新/删除/权限测试 |
| B05 | 五类 Wiki 专题和可读视图，双向质量检查 | 同一真实主题完整闭环，逐项可追溯 |
| B06 | 统一检索路由、分解查询、回答与逐项引用 | 精确事实及跨章节问题；预算/拒答测试 |
| B07 | Procedure 与现有 Action/Workflow 编译衔接 | 不新增无来源操作；审核和执行状态不越界 |
| B08 | 构建锁、断点续作、原子激活、回退、索引与缓存一致性 | 中断/并发/失效回退测试 |
| B09 | 固定评测集、四组比较、失败分析及定向修复 | 独立标注记录；留出集质量报告 |
| B10 | CLI/MCP/HTTP 接入、部署与迁移说明、端到端交接 | 本地真实资料闭环，兼容回归，最终交付清单 |

早期即选取至少一个真实流程做垂直样例，贯穿导入、事实、专题、回答和引用；不能到 B09 才首次使用真实资料。

缺模型凭据时可以完成存储、schema、stub 和确定性测试，不能把 B03/B05 的真实语义质量验收标成通过。缺资料/版本时继续可独立任务，同时保留待办。

## 11. 定时任务执行协议

### 11.1 状态与交接文件

CC 首次执行时创建：

```text
docs/implementation/kb/PLAN.md          # 批次与验收 checklist
docs/implementation/kb/STATE.json       # 机器可读断点
docs/implementation/kb/PROGRESS.md      # 每次运行的事实记录
docs/implementation/kb/DECISIONS.md     # ADR 与设计偏差
docs/implementation/kb/BLOCKERS.md      # 依赖、影响、所需外部输入
```

STATE 至少包含 schema_version、run_id、当前批次、子任务、状态、输入/产物哈希、验证命令及结果摘要、最后完成点、下一动作、阻塞项、更新时间。运行锁在外部运行目录，避免污染 Git。

### 11.2 每次唤醒流程

1. 读取适用 AGENTS.md、本文、STATE 和最新进度；核对 git status，不覆盖外部修改。
2. 获取带 owner、心跳和租约的独占锁。已有有效执行者时退出；过期锁经确认无活跃进程后恢复，防止并发写同一状态或源码。
3. 核对上次断点与实际产物，选择最早可推进且尚未验收的子任务。
4. 完成实现并执行相关验证；修改公共契约时扩展回归。把命令、退出码、真实/模拟模式写进记录。
5. 原子更新状态和进度，再释放锁。未通过验收的任务不能标 done。
6. 临近调度时限时停止领取新任务，保存可恢复断点；不能仅因本次时限到达而宣告整体完成。

暂定每次运行 45 分钟，预留最后 5 分钟保存断点；调度间隔由用户配置，锁机制必须能容忍前次超时。模型调用使用超时、有限重试及退避；连续三次相同失败转阻塞并保留诊断，继续无依赖任务，避免反复消耗。

### 11.3 自主范围与完成判定

可自主进行：本地实现、测试、资料解析、候选知识编译、评测、文档和可回退的本地快照构建。新模块可重构，但应保留迁移路径。

不得伪造人工审核、实机结果或模型评测；不得清理用户未提交内容；不得把未知版本默认合并；不得擅自推送、部署、发送外部消息或操作真实终端。Git 提交仅按用户另行约定执行，不能把预存修改混入本任务。

通知仅用于有意义的里程碑、需用户处理的阻塞、重大失败或完成；没有进展时不重复发送同样状态。此处通知指调度器的结果反馈，不授权向第三方发送消息。

最终完成需要 B00–B10 验收清单、真实模型评测、独立标注留出集及最终交接齐全。若只缺人工评审或真实环境，状态应为 implementation_complete_pending_validation，并列出缺项，不能写全部完成。达到目标后停止自动扩展功能。

## 13. 最终交付清单

- 可安装运行的代码，明确依赖与离线模型配置，CLI/MCP/HTTP 共用契约。
